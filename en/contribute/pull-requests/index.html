Admission criteria

Four checks for every proposed task

01

Scientific importance

A better result would advance a real research question or an important scientific computing bottleneck.

02

Verifier credibility

The scoring algorithm, inputs, constants, tolerances, aggregation and invalid-output rules can be fixed and run locally, offline and deterministically.

03

Frontier headroom

The best achievable result remains unknown, with credible evidence of meaningful room for improvement.

04

Long-term sustainability

Data, software and the verification path can remain available without fragile services, secret credentials or irreproducible external behavior.

A final score cannot depend on new wet-lab experiments, future data or labels, human judgment, or an organizer-operated service.

Formal task package

Accepted tasks use one five-part contract

A proposal does not need to arrive in this directory layout. The project team reviews the supplied materials and extracts the minimal running contract.

01

instruction.json

Agent-facing instructions, declared inputs, required submission artifacts, provided environment, confirmed requirements and enforced limits.

02

input/

Only Agent-visible scientific inputs, task instances and optional submission templates.

03

environment/

An executable environment.json selects the operator-locked default image or a task Containerfile.

04

verifier/

Fixed Validation and Test programs provide research-time feedback and final scoring through two required entry points.

05

meta.json

Task identity, immutable source identity, data sources, raw metric semantics and a frozen public-score mapping when defined.

Baselines, full construction evidence, tests and review history are maintained separately from the formal task package.

Review process

How a proposal is handled

01

Submit a proposal

Open a GitHub Discussion and describe the scientific question, task design and scoring method. Confirm material permissions and optionally add references.

02

Independent review

An assigned Reviewer assesses the four admission criteria and may request a revision.

03

Maintainer decision

A maintainer records a decision for the current proposal through GitHub Actions. Editing the approved content requires renewed approval.

04

Open a task PR

After approval, use the Proposal number to open a five-part task-package PR in the contribution repository.

05

Domain and technical review

Two different reviewers record the scientific and implementation conclusions. Passing CI and both approvals are required before merge.

Responsibilities

What contributors provide and what the project team handles

Contributor materials

  • Scientific value, unresolved evidence and frontier headroom
  • Agent inputs, required submission artifacts, environment needs and hard constraints
  • Existing scoring algorithm, code and required data
  • Data, software and model sources, licenses and access paths
  • Credible Agent and Verifier resource requirements
  • What the score can and cannot support scientifically

Project team review

  • Independently verify the scientific evidence and admission criteria
  • Review Verifier credibility and attack surface, then add deterministic packaging and tests
  • Maintain construction history and extract the formal five-part package
  • Run accepted tasks under controlled conditions and publish reviewed results
