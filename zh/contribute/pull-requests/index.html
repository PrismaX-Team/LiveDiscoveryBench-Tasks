在 GitHub Discussions 公开提交 Proposal 并跟进反馈和修订。正文、链接与评论都会公开；请勿提交私人邮箱、敏感信息或无权公开的材料。

共建政策

01

共同作者

至少有 1 个任务包通过审核并被采纳的贡献者，可成为项目论文共同作者；需配合完成任务核验、内容修订和作者信息确认。

02

审核者与核心维护者

被采纳任务包超过 4 个的成员，有机会受邀担任 reviewer，并进入核心维护者路径。这是邀请，不是自动授予。

审核流程

  1. 01

    提交 Proposal

    在 GitHub Discussions 中说明科学问题、任务设计与评分方式，确认材料使用权限；参考材料可选。

  2. 02

    独立审核

    被分配的 Reviewer 按四项准入条件审核，并可要求提交新修订。

  3. 03

    维护者决定

    维护者通过 GitHub Actions 记录当前 Proposal 的决定；修改获批内容后须重新确认。

  4. 04

    创建任务 PR

    获准后，使用 Proposal 编号在贡献仓库中提交五部分任务包 PR。

  5. 05

    领域与技术审核

    两位不同的 Reviewer 分别记录科学与实现结论；CI 通过且两个审核席都批准后才可合并。

公开进展

Proposal 与 Task PR

公开查看 Proposal、新任务与任务修复的进展。任务 PR 须通过领域与技术双审。

准入条件

每个任务建议分别通过四项检查

01

科学重要性

结果变好后，应能推进真实研究问题或重要科学计算瓶颈。

02

Verifier 可信度

评分算法、输入、常数、容差、聚合和无效输出处理能够完整固定，并在本地、离线、确定性运行。

03

前沿空间

当前最佳可达结果仍未知，并有可信证据表明存在实质改进空间。

04

长期可持续性

数据、软件和验证路径能够稳定获得，不依赖脆弱服务、秘密凭证或不可重复的外部行为。

如果最终分依赖新的湿实验、未来数据或标签、人工判断或组织方服务，任务不符合准入要求。

正式任务包

通过审核的任务采用五部分合同

共建者不需要一开始就整理成最终目录。项目团队核查已有材料，并从中抽取最小运行合同。

01

instruction.json

面向 Agent 的任务说明、输入声明、提交产物、已提供环境、确认后的要求和实际施加的限制。

02

input/

只包含 Agent 可见的科学输入、任务实例和可选提交模板。

03

environment/

可执行的 environment.json 选择运营方锁定的默认镜像或任务专用 Containerfile。

04

verifier/

固定的 Validation 与 Test 程序通过两个必需入口分别提供研究阶段反馈和最终评分。

05

meta.json

任务身份、不可变来源身份、数据来源、原始指标语义，以及定义后冻结的公共分数映射。
